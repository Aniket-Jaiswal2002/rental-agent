# Voice renter-intake agent

A small voice-first agent that takes a renter from "I need a home" to a confirmed search profile and a grounded
top-3 shortlist of Gurugram rentals. It is built to show memory, tool use, planning, evals and messy real-world
input (Hinglish, corrections, contradictions, vague requests) working end to end.

> **All listing data is SYNTHETIC.** `data/listings.json` holds 30 fabricated listings generated by
> `scripts/gen_listings.py`. Sector names are real places; prices, distances, availability and descriptions are made up.

## What it does

1. **Talks.** Push-to-talk in the browser → Groq Whisper speech-to-text → agent → reply spoken by the browser.
   English and Hinglish input both work; the agent always replies in English.
2. **Remembers.** A structured `RenterProfile` (Pydantic) is the agent's memory, separate from the chat history.
   It is updated every turn and shown live in the side panel, with a changelog. Corrections ("actually make it
   35k", "nahi, 35 kar do") update the profile and are announced as `old -> new`.
3. **Plans.** It asks for missing required fields (budget, areas, BHK, move-in date, commute destination), then
   reads the profile back. It only searches after the renter explicitly confirms.
4. **Uses a tool.** `search_listings` filters and ranks the dataset using the confirmed profile.
5. **Stays grounded.** It returns up to 3 listings with a one-sentence trade-off each. Rent, deposit, area and
   every other listing fact are rendered from the dataset by the server, never written by the model.
6. **Says no.** When nothing matches it says so and shows nothing, instead of forcing a bad match.

## Architecture

```
 browser (web/)                          server (FastAPI, app/server.py)
 ┌────────────────────────┐   audio      ┌──────────────┐
 │ hold-to-talk           │ ──────────▶  │ POST /stt     │──▶ Groq Whisper (whisper-large-v3-turbo)
 │ transcript + cards     │   text       ├──────────────┤
 │ memory panel           │ ──────────▶  │ POST /chat    │──▶ Agent.turn()  (app/agent.py)
 │ latency strip          │ ◀──────────  └──────────────┘        │
 │ speechSynthesis (TTS)  │  reply, profile, shortlist, timings   │
 └────────────────────────┘                                       ▼
                         ┌──────────────────────────────────────────────────────────────┐
                         │ system prompt + STATE (profile, missing fields, flags,        │
                         │   last_asked, latest search) + last 3 turns of chat           │
                         │        │                                                      │
                         │        ▼                                                      │
                         │   LLM (Groq, openai/gpt-oss-120b) ──tool calls──▶ tools.py    │
                         │        update_profile(changes, change_kinds)                 │
                         │        confirm_profile(renter_quote)                          │
                         │        get_listing(id)                                        │
                         │        respond(reply, asking_for, shortlist, no_match_notice) │
                         │                                                               │
                         │   code-driven steps (no LLM call):                            │
                         │     profile complete + unconfirmed → read-back from template  │
                         │     confirmed → search_listings (app/listings.py)             │
                         │     shortlist ids validated → facts rendered from JSON        │
                         └──────────────────────────────────────────────────────────────┘
```

Key files: `app/agent.py` (loop, validation, rendering), `app/profile.py` (memory, change kinds, confirmation
gate), `app/listings.py` (search), `app/dates.py` (relative move-in dates), `app/llm.py` (Groq client, pacing),
`app/voice.py` (speech-to-text), `evals/` (cases, checks, runner, report).

## Run

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env                                # then add GROQ_API_KEY
.venv\Scripts\python -m pytest -q                     # offline tests, no API calls
.venv\Scripts\python -m uvicorn app.server:app --port 8000   # open http://localhost:8000 in Chrome
.venv\Scripts\python -m app.cli                       # text-only chat
```

**UI without tokens:** with `FAKE_LLM=1`, a canned rule-based stand-in replaces the model, so the UI can be built
and screenshotted at zero cost. Every turn still goes through the real agent loop, memory, confirmation gate,
search and rendering.

```bash
set FAKE_LLM=1
.venv\Scripts\python -m uvicorn app.server:app --port 8010
```

## Evals

```bash
.venv\Scripts\python -m evals.run                     # one full pass; stops cleanly if the Groq quota runs out
.venv\Scripts\python -m evals.run --resume            # next quota window: finishes the remaining cases
.venv\Scripts\python -m evals.report evals/raw/<pass>.json   # renders evals/results.md
```

There are 12 scripted conversations in `evals/cases/`:

| # | Case | What it probes |
|---|---|---|
| 01 | vague renter | asks for every required field |
| 02 | budget change midway | correction applied, announced and re-confirmed |
| 03 | contradictory info | conflict is not applied; the agent asks |
| 04 | Hinglish renter | spoken numbers, mixed language |
| 05 | no match | says so, shows nothing |
| 06 | nonexistent listing | looks it up, says it doesn't exist |
| 07 | everything in one sentence | read-back with zero extra questions |
| 08 | pets + bachelor | optional constraints respected |
| 09 | self-correction | replace, not append |
| 10 | prompt injection | nothing shown before confirmation, no prompt leak |
| 11 | change after confirming | confirmation resets; second read-back before second search |
| 12 | "Gurgaon", 5 BHK, "within a week" | city is not an area; relative date resolved; no forced match |

The checks are deterministic. They read the tool log, the structured `asking_for` field, the profile snapshots
and the dataset; there is no LLM judge and no pattern-matching of model prose:

- **(a)** every required field that was missing was asked about before the first search, and no search ran
  before confirmation;
- **(b)** the final profile equals the expected profile (unlisted fields must be empty);
- **(c)** every shortlisted id was in the latest tool result and exists in the dataset, rendered facts equal
  the JSON, and hard constraints hold;
- **(d)** an empty search gives an empty shortlist and a no-match notice;
- **(e)** case-specific expectations;
- **(f)** no fallback replies.

## Latency

Each turn logs `stt_ms`, `llm_ms` (model round trips only), `wait_ms` (client-side quota pacing and backoff,
kept out of model time), `tool_ms`, `tts_ms` (browser: time to start speaking) and `total_ms` to
`logs/latency.jsonl`. The UI shows the last turn's breakdown.

LLM calls per turn by design: **1** for an intake turn or a correction (update and reply in one response; the
read-back is rendered in code), **2** for a confirmation turn (confirm, then the shortlist after the code runs
the search).

## Design decisions

- **Grounding by construction.** The model's final answer is a structured `respond` call. A shortlist is a list
  of `{listing_id, tradeoff}`, and ids must come from the latest search or lookup result (others are bounced
  back to the model). The server renders rent, deposit, area and every other fact from `listings.json`. The
  one-sentence trade-off is the only model-written text about a listing.
- **Structural confirmation gate.** The read-back sets `awaiting_confirmation`. `confirm_profile` is accepted
  only on the very next renter turn, with a quote that must appear in the renter's message. Any real profile
  change clears both flags and the stale search. Searching is impossible until confirmed.
- **Structured `change_kind`.** Every profile update labels each field `new`, `correction` or `conflict`, and
  the code enforces the contract: overwriting a stored value as `new` is rejected, a `conflict` is never
  applied and the reply must ask about it, and a `correction` is announced `old -> new` by the app. There are
  no keyword lists. "Gurgaon" alone is treated like a conflict: it is the whole city, so the agent asks for
  sectors.
- **Search uses the confirmed profile.** `search_listings` takes no model-supplied filters, so the model cannot
  drift from what the renter agreed to.
- **Eval check (a) counts volunteered fields as handled.** A required field the renter volunteers without being
  asked does not fail "asked before searching".
- **Fewer LLM calls per turn.** The read-back is a template, the search after confirmation runs in code, and
  one response can carry an update and the reply. `reasoning_effort` is `low`.
- **Relative dates in code.** "Within a week", "agle mahine" and "1st December" are resolved by `app/dates.py`
  against today's date. Evals pin "today", so results are reproducible.

## Built on free-tier limits

The whole demo runs on Groq's free tier (`openai/gpt-oss-120b`: about 8K tokens/minute and a daily token cap).
That shaped a few choices:

- **Token pacing.** The Groq client sleeps *before* a request if it would push the last 60 seconds over
  `GROQ_TPM` (7,000) tokens, instead of retrying into 429s. Real 429s are retried with exponential backoff
  and honour `retry-after` up to `GROQ_MAX_WAIT_S`. This waiting is logged as `wait_ms`, separate from model time.
- **Prompt trim.** Shorter system prompt and tool schemas. Prompt tokens per call, measured with
  `python -m scripts.probe_tokens` (Groq's own usage numbers):

  | Scenario | Before | After |
  |---|---|---|
  | Fresh (first message, empty profile) | 2,053 | 1,452 |
  | Mid-conversation (turn 10, full profile, search result, 9 earlier turns) | 2,441 | 1,624 |

- **Last-3-turn history, profile as memory.** Only the last 3 renter/assistant exchanges are resent. Everything
  older lives in the structured profile (plus `last_asked` and the latest search summary) injected into every
  call, which is the memory the agent is meant to rely on anyway.
- **Eval runs split across quota windows on one commit.** One run per case (three were planned). A pass stops
  cleanly when the quota runs out and `--resume` finishes the remaining cases later. Resuming is refused if the
  code changed, the tree is dirty, or the model differs, so every result in a pass comes from one commit (the
  pass runs from a git worktree pinned to that commit while development continues).

## Known limitations

- **Synthetic data.** Distances are approximate and known only to Cyber City and Golf Course Road.
- **Voice quality depends on the browser.** TTS uses the browser's voices, so quality and Indian-English
  availability vary by OS. Push-to-talk only: no streaming STT, no voice-activity detection.
- **Heavy Hindi.** Whisper may return Devanagari for heavily Hindi speech. The prompt biases toward romanised
  text, and the agent copes, but this is lightly tested.
- **The model still judges intent.** The code enforces the `change_kind` contract, but deciding whether
  something is a correction or a conflict is still the model's call.
- **Trade-off sentences are model-written.** Their numbers come from tool-result fields, but the sentence
  itself is not verified.
- **Small eval sample.** One run per case on a non-deterministic model: a pass rate from 12 runs is indicative,
  not a benchmark.
- **No persistence.** Sessions live in memory, and there is no auth.
- **Limited date phrases.** The relative-date resolver covers a fixed set of English and Hinglish phrases;
  anything else makes the agent ask for a date.

## What I'd build next

- **Broker follow-ups:** message the listing's broker with the renter's confirmed profile, and track replies.
- **Visit scheduling:** propose slots and book them against broker availability.
- **WhatsApp intake:** the same agent and memory behind a WhatsApp number (voice notes → STT).
- **Streaming voice:** streaming STT and TTS with an Indian-language provider (e.g. Sarvam) for lower latency and
  natural Hinglish voices.
- **Persistence and handoff:** saved profiles across sessions and a human-agent view of the same memory panel.
- **Bigger evals:** more cases, 3+ runs per case on a paid tier, plus a small LLM-judged tone/helpfulness
  layer on top of the deterministic checks.

## How this was built

Built with [Claude Code](https://claude.com/claude-code) as the implementation tool. I set the scope and made
the design calls; Claude Code wrote the code and tests under those constraints and ran the checks. The decisions
that shaped the system were mine:

- **Grounding by construction**, not prose checking: structured shortlist ids, with facts rendered by the
  server.
- **A structural confirmation gate**: read-back → next-turn confirmation with a verbatim quote → search.
- **Structured `change_kind`** (`new` / `correction` / `conflict`), enforced in code, replacing an earlier
  keyword-list guard.
- **Eval honesty rules**:
  - deterministic checks only;
  - a failing check means fixing the agent, not the check;
  - rate-limited runs reported separately from failures;
  - the headline is the first full pass on one clean commit, with model and commit SHA recorded per run;
  - follow-up runs are listed beside the first result, never replacing it;
  - `results.md` is rendered from raw data, never hand-edited.
- **Fewer LLM calls per turn**: code read-back, single-response updates, auto-search after confirmation,
  `reasoning_effort` low, and model time logged separately from quota waits.
- **Working within free-tier limits**: token pacing, prompt trim measured with a probe, last-3-turn history
  with the profile as memory, and resumable eval passes split across quota windows on one commit.
